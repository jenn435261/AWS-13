Every judgement call made during the overnight run (branch `kiro/overnight`) is recorded here with its rationale. Subsequent features append their own decisions below.

## 2026-10-24

### Certificate issuance depth limit = 2

A certificate chain originating from a trusted root may be at most **2 hops deep**. That is, a trusted root may issue to an intermediate authority, and that intermediate may issue to a leaf — but a leaf certificate may not itself act as an issuer beyond that depth.

- Source: spec section 8 open policy question (`docs/SPEC_PROVIDER_AND_FEATURES.md`), pre-specified for this run.
- Rationale: bounds trust propagation so a single compromised intermediate cannot mint arbitrarily long chains; keeps verification cost and the trust surface small for an offline-first network where roots are distributed out of band.
- Applies wherever certificate chains are validated (trust engine / trust roots). Chains deeper than 2 hops from a trusted root are rejected.
- **Enforcement detail (FEAT-005).** Implemented in `OrgCertGraph.provenanceOf` (`app/lib/trust/org_certs.dart`) as a depth-bounded breadth-first walk up the issuer graph from the subject, with `OrgCertGraph.maxChainDepth = 2`. A trusted root is depth 0 (it certifies itself); a key a root certifies directly is depth 1; a key certified by that key is depth 2; a key one further hop out is depth 3 and is NOT granted the badge. BFS by depth means the SHORTEST chain to a root decides, so a key reachable at depth ≤ 2 by any path still verifies even if a longer path also exists. Revoked keys on a path still break that path, and a visited set defeats cycles. Proven by `derived_state_test.dart` "certificate chain depth limit: depth 2 verifies, depth 3 does not".

### FEAT-002 (Item A) — app-side cloud + node sync client

- **JSON on the wire (not protobuf).** Both the cloud API (`cloud/internal/api/server.go`) and the node sync server (`node/internal/syncserver/server.go`) content-negotiate protobuf-or-JSON. `CloudSync` sends `Content-Type: application/json` + `Accept: application/json` and serializes via `toProto3Json()`/`mergeFromProto3Json`. Rationale: JSON is the most portable choice, works identically on Flutter web (where `dart:ffi` protobuf quirks are a risk) and native, and keeps the request/response inspectable. Byte volume is not a concern at the batch sizes involved, and the content is already signed so there is no integrity loss.
- **One class, two endpoint kinds.** A single `CloudSync` class is parameterized by `SyncEndpointKind` (`cloud` → `/v1/events` + `/v1/events/pull`; `node` → `/node/v1/push` + `/node/v1/pull`) rather than two near-identical classes. The request/response proto types are shared by both servers, so this avoids duplication.
- **Cursor storage scheme.** Push high-water marks live in the existing `KeyValue` table via `JsonStore` under the `sync:` prefix, one row per endpoint keyed `pushhw:<kind>:<baseUrl>`. The **pull** side needs no stored cursor: the per-author high-water digest is derived live from `EventDao.highWaterByAuthor()`, so pulls are naturally incremental and idempotent. "N pending" = count of our own events (`eventsByAuthorFrom(myAuthor, pushHighWater)`).
- **Ingestion path.** Every pulled event is applied through `EventStore.applyAll` → `EventStore.apply`, the single verify-then-store path, so a forged/tampered event fails `EventFactory.verifyEvent` and is never stored (proven by `app/test/cloud_sync_test.dart` and the Go `TestServerPushVerifiesAndPulls`). After a round that applied anything new, `bumpWorldRef(ref)` recomputes the folded `WorldState`.
- **Backoff policy.** Exponential backoff starting at 1s, doubling, capped at 2 minutes; reset to zero on a clean round. A 30s periodic timer drives syncs while the app is visible; sync also fires on start, on `AppLifecycleState.resumed`, and after every local write (observed via `worldRevisionProvider`). Concurrent rounds are coalesced (a `_running` guard) so overlapping triggers do not stack.
- **Honest failure.** `syncOnce()` never throws: timeouts (10s on every HTTP call) and non-200 responses are captured in `SyncOutcome.error` and surfaced as a truthful message on the Network Status screen. No active node saved ⇒ node sync is a no-op, not an error.
- **Two-profile scenario: Go-level substitute, not a browser run.** The browser two-profile click-through was NOT run (see OVERNIGHT_LOG for the reason). It was substituted with `TestTwoProfileSyncThroughCloud` in `cloud/internal/api/server_test.go`, which runs a real local cloud API (`httptest`) and two distinct Ed25519 identities: profile A publishes a help request, a supply, an emergency alert and an identity certificate; profile B pulls from an empty watermark and receives all four byte-identical (so the verified/community provenance in the body is preserved), then a re-pull from the new watermark returns nothing (idempotence).

### FEAT-003 (Item B) — secure messaging with photos and audio

- **Prekey distribution rides the event log, not a new endpoint.** A device publishes its X3DH prekey bundle as a signed `EVENT_TYPE_PREKEY_BUNDLE` event (`MessagingService.publishMyBundle`), so it flows over the existing FEAT-002 sync client with no new cloud/node route. A chat is started by folding the log for the contact's most recent `PREKEY_BUNDLE` event (`_latestBundleBody`) and running `SessionBuilder.processPreKeyBundle`. Rationale: one transport for everything, verify-before-store already applies, and it keeps the cloud API surface minimal. The alternative (a gated `/v1/prekeys/{id}` endpoint) was rejected as redundant.
- **Durable Signal store = Drift write-through over the vetted libsignal records.** `DriftSignalProtocolStore` (schema v2) keeps the fast in-memory libsignal stores hydrated from Drift and writes each mutation (identity, one-time prekeys, signed prekeys, sessions, group sender keys, trusted remote identities) straight back as the record's own `serialize()` bytes. We never invent a key format. A migration (`onUpgrade` v1→v2) adds the six `Signal*` tables; `wipeAll()` erases them. Proven to survive a restart by `drift_signal_store_test.dart` (a session established before "restart" keeps decrypting after reloading the store from the same DB).
- **Attachment envelope: `MessagePayload{kind,text,attachments[]}` inside the Signal ciphertext.** Per spec §6, the file itself is AES-256-GCM encrypted with a random 256-bit key and uploaded as ciphertext to the content-addressed blob store; only a small `Attachment{sha256,size,mime,key,thumbnail,...}` descriptor (carrying that key) travels inside the E2E-encrypted `MessageBody.ciphertext`. So a relay holding the blob cannot read it (it never sees the key), and a relay carrying the message cannot read it (Signal ciphertext). Ciphertext layout: `[12-byte nonce][AES-GCM ct+tag]`; the content address is `sha256(ciphertext)`, verified after download AND before display (`decryptAttachment` throws on mismatch or GCM auth failure). Blobs addressed by **sha256** (not blake2b) to match the Go `/v1/blobs/{sha256}` API; event ids keep blake2b.
- **Blob endpoints: in-memory, content-addressed, abuse-guarded.** Cloud `/v1/blobs/{sha256}` (client-key gated via `clientGate`) and node `/node/v1/blobs/{sha256}` (local Wi-Fi, no key). 2 MiB cap, the path sha256 must equal `sha256(body)` on PUT (else 400), a fixed-window per-caller write rate limit, and a 7-day purge. Stored in memory mirroring each server's existing style. A dedicated Go test asserts the stored bytes are **only ciphertext** (never the plaintext or key).
- **Outbound bubble mirror.** We cannot decrypt our own Double-Ratchet ciphertext, so `MessagingService` keeps a local-only durable mirror of each outbound `MessagePayload` in the `KeyValue` table (`msgmirror:` prefix) to render our own sent bubbles. It never leaves the device.
- **Media packages (web-safe).** `image` (pure-Dart decode/re-encode + **EXIF/GPS strip** by clearing all metadata before `encodeJpg`), `image_picker`, `record` (hold-to-record mic, web via MediaRecorder), `audioplayers` (playback). `maplibre_gl` was NOT added (breaks web build). `flutter build web --release` verified to still succeed after adding them. Photos are downscaled to ≤1600px with an ≤8KB inline thumbnail (`preparePhoto`, proven to strip EXIF by `photo_prep_test.dart`); audio is AAC mono, hold-to-record, ≤60s, with cancel/play/duration.
- **Direct tab only.** The honest "not connected" state was removed only on the **Direct** tab, and only now that text+photo+audio truly work end to end. Community and Mission tabs keep honest "not wired yet" states. If no contacts exist, Direct shows the honest no-contacts state.
- **Browser click-through: booted + blob exercise; UI-driving substituted.** The two profiles were booted same-origin through the cloud (zero console errors) and the cloud+node blob endpoints were exercised A→B at the HTTP/crypto layer (encrypt with a random key, PUT ciphertext to both, assert the server held ONLY ciphertext, B decrypts, 401 without the cloud key, 400 on hash mismatch). Driving the Flutter semantics tree to add contacts and compose a photo/voice note was NOT done: a headless browser has no microphone (hold-to-record is unobservable) and `image_picker`'s native file dialog cannot be driven headlessly. These are backed instead by the passing Dart A→B text+photo+audio round-trip test (`messaging_e2e_test.dart`, incl. the tampered-ciphertext abuse cases) and the Go ciphertext-only assertions. See OVERNIGHT_LOG for exactly what ran vs. substituted.

### FEAT-004 (Item C) — location sharing

- **"Until I stop" expiry sentinel = now + 7 days.** The spec says every share MUST carry a finite `expires_ms`, but the UI offers an "until stopped" duration with no natural end. Decision: the "until stopped" chip maps to `expires_ms = now + 7 days` (`LocationShareScreen.kUntilStoppedTtl`). Rationale: it satisfies the always-set-expiry invariant and the self-expiry safety property (a share can never live forever even if the sharer never sends `LOCATION_STOP` and never comes back online), while 7 days is long enough that an intentionally persistent share is not surprising. The user can always revoke earlier with Stop (which publishes `LOCATION_STOP`). The 30-minute `kDefaultShareTtl` in `location_share.dart` is unchanged and only applies when a caller passes no ttl.
- **Fold is the authoritative active-shares read-model; it never decrypts.** `WorldState._recompute` folds `EVENT_TYPE_LOCATION_SHARE`/`EVENT_TYPE_LOCATION_STOP` into `WorldState.locationShares`, keeping the latest share per `(author, shareId)` (highest `seq`, then lamport) and dropping any share that has expired (`now >= expiresMs`, using the injected `clock`) or been stopped. The fold carries `encryptedPoint` **opaquely** and never decrypts or logs a coordinate; resolving the precise point for an authorized viewer happens later in `ActiveShares.incomingFor`/`incomingSharesProvider` using that viewer's own Signal sessions. `WorldState.locationSharesVisibleTo(viewerPubkey, channelIds, includePublic)` is the audience filter the map/list use.
- **Abuse rule — only the sharer can stop/expire their own share.** `LOCATION_STOP` is folded **per author**: a stop only affects shares whose author matches the stop's author. So a forged stop by a non-owner (C) for A's `shareId` cannot revoke A's share (proven by `location_share_test.dart` "abuse: C cannot stop A's share"). And a non-audience contact never sees a share not addressed to them: `locationSharesVisibleTo` returns only `contact:<viewerHex>` matches, public beacons, and channels the viewer is in, so C's visible set is empty and C's unrelated Signal session cannot decrypt A→B ciphertext (both proven in the fold tests). No plaintext coordinate can leak to C.
- **E2E path reused from FEAT-003.** The precise `GeoPoint` is encrypted per contact over the SAME durable Signal 1:1 session used for messaging: `MessagingService.outboundSessionFor(contactPubkey)` (establishes X3DH from the contact's published prekey-bundle event if needed) on send, `inboundSessionFrom(sharerPubkey)` on view. `LocationCoordinator` ties the position read + encryption + event emit together; a contact with no published bundle is reported `unreachable` and skipped (honest state), not a crash.
- **Precision default = approximate (~110 m).** The precise point is rounded via `geoPointFor(..., exact:false)` (3 decimals, ~110 m) unless the user explicitly picks "Exact location". Public beacons always publish only the coarse `publicPoint` (guarded by `LocationSharer._assertPublicBeacon`); contact/channel shares put the precise point only in `encryptedPoint` (guarded by `_assertNoClearPoint`).
- **Stop control stops ALL of the local user's shares.** The screen's Stop button publishes a `LOCATION_STOP` with an empty `shareId` (author-wide revoke) so it reliably clears whatever is active regardless of which share id was started. Per-share stop (`stop(shareId: ...)`) remains available in the coordinator API.
- **Map marker style.** People sharing their location WITH this device render as a distinct teal `person_pin_circle` (`AppTheme.sharing = #00897B`), visually separate from supplies (verified green / community purple) and help requests (urgent red), plus an "N sharing" chip that opens a list sheet. The `location_not_connected` note and the `onPressed:null` Share button were removed now that delivery works end to end.
- **Browser click-through: booted in two profiles with geolocation; share-flow UI-driving substituted by the Dart fold tests.** See OVERNIGHT_LOG for exactly what ran vs. substituted.

### FEAT-005 (Item D) — provider completeness, `HELP_REQUEST_CLOSED`, depth limit

- **New event type `EVENT_TYPE_HELP_REQUEST_CLOSED = 24` + `HelpRequestClosedBody`.** Added to `proto/resilience/v1/event.proto` using the next unused number in the Help flows block (20–23 were taken). Body carries `request_id`, optional `reason`, optional `closed_at_ms`. Regenerated with `cd proto && buf generate` (protoc-gen-go v1.36.12 + protoc-gen-dart) and the regenerated `event.pb.go`/`sync.pb.go` were copied over `node/gen/resilience/v1/` (node/gen is a vendored byte-identical copy; `buf.gen.yaml` does not emit there). `git status` on the gen dirs showed only the intended enum/message additions.
- **Request close is owner-only, modeled as fold state not deletion.** `WorldState._recompute` folds requests per `request_id` (first author owns the id; a later `HELP_REQUESTED` under the same id from a different key cannot hijack it). A `HELP_REQUEST_CLOSED` sets `HelpRequestView.closed` **only** when authored by the request's owner; a close from any other key is ignored (abuse rule). The closed request stays in the projection (struck through, "Closed" in My Requests) but is filtered off the shared map, so history stays verifiable. Proven by the two `derived_state_test.dart` close tests (owner closes; non-owner ignored).
- **Alert recall = re-issue the same `alert_id` with `expires_ms` in the past, author-only.** Alerts fold per `alert_id`; the latest event by the alert's **original author** wins (a different verified org cannot supersede or recall someone else's alert). The materialize step drops any alert whose latest `expires_ms` is ≤ now (which covers both natural expiry and an author recall). The provider screen's "my alerts" rows show a **Recall** action for still-live alerts that publishes a fresh `EMERGENCY_ALERT` with the same id and an expiry one minute in the past. Proven by `derived_state_test.dart` "alert recall …".
- **Auto-hide expired supplies.** `ResourceView.isExpired(now)` is true when `available_until_ms > 0 && available_until_ms ≤ now` (relative to the fold's injected clock). New `WorldState.mapResources()` returns ranked resources excluding withdrawn AND expired supplies; `map_screen.dart` now uses it. The owner still sees the supply in My Supplies, marked **Expired**. Proven by `derived_state_test.dart` "a supply past available_until_ms is auto-hidden …".
- **Mission create/assign is verified-provider-only.** `MissionStore.missionsForViewer` gained an optional `isVerifiedProvider(author)` predicate; `missionsProvider` passes `WorldState.provenanceOf(author) == VERIFIED_ORG`. A `MISSION_CREATED` or `MISSION_MATCHED` signed by a non-verified key is ignored (abuse rule). Carriers accept via `MISSION_ACCEPTED` (its own author signature). `DeliveriesScreen` renders the `MissionBucket` board (Assigned / Available / In transit / Awaiting handoff / Completed); a provider assigns a contact as carrier via `MISSION_MATCHED`, a carrier accepts via `MISSION_ACCEPTED`. Proven by `mission_chain_test.dart` "a verified provider may create+assign … a non-provider … is ignored".
- **Browser click-through: booted two profiles same-origin; UI-driving substituted by the Dart fold/abuse tests.** Same confirmed headless-semantics limitation as FEAT-003/004 (no aria-label nodes), so the assign/recall/close/accept interactions are NOT tappable headlessly; the authoritative proof is the passing Dart suite. See OVERNIGHT_LOG for exactly what ran vs. substituted.

### FEAT-006 (Item E + F) — offline PMTiles map and remaining AI endpoints in the UI

- **PMTiles rendering approach (web-safe, why it is).** The chosen approach reads the node's `/node/v1/map/{region}.pmtiles` with `PmTilesArchive.fromUri` (the `pmtiles` package's HTTP backend over Range requests) and decodes **raster** tiles (png/jpeg/webp) with the Flutter engine's own `ImmutableBuffer.fromUint8List`, wired into `flutter_map` as a custom `TileProvider` + `ImageProvider` (`app/lib/ui/map/pmtiles_tile_provider.dart`). It is web-safe because: (1) the `pmtiles` package's own support matrix lists HTTP as working on dart2js/browsers (only its File backend is native-only, and we never call `fromFile`); (2) decoding goes through the standard Flutter image codec, so no extra renderer is pulled in; (3) crucially `maplibre_gl` is NOT added — its web plugin breaks `flutter build web --release`, which is the hard gating limit for Item E. The gating check `flutter build web --release` was run and passed with the PMTiles import in the tree.
- **Raster-only; vector archives fall back to OSM (honest, no silent blank).** We do not ship a vector-tile renderer (that would need maplibre_gl or a vector_tile_renderer, out of scope and/or web-breaking). `PmTilesTileProvider.openRaster` therefore returns null for mvt/mlt/unknown archives, for an unreachable node, or for any parse error, so `MapView` transparently keeps the online OSM raster layer and the honest offline banner rather than showing nothing. Proven by `map_pmtiles_test.dart` (unreachable + garbage URL → null, never throws).
- **Region discovery via the node catalog, not a guessed name.** Rather than hardcode a region file name, `nodePmtilesUrlProvider` fetches the active node's `/node/v1/packages` catalog and uses the first `kind == "map"` item's `path`. No active node or no map item ⇒ null ⇒ OSM online fallback. This keeps the app honest about what the node actually serves.
- **`AiAssist.summarize` returns `SummaryResult{text,degraded}` (client contract change only).** The old `summarize` returned a bare `String`, which could not carry the degraded flag, so the Home summary could not honestly distinguish a live Bedrock answer from the rules fallback. Changed the Dart `AiAssist` contract to return `SummaryResult` and read the `degraded` boolean straight from the existing `/v1/ai/summarize` response (`{summary,degraded}`). The HTTP endpoint contract is unchanged, so `cloud/internal/api/server_test.go` was intentionally left untouched. The Home degraded chip now shows iff the response/`fallback` is degraded — never implying a live model when rules produced the text.
- **Translate is additive and honest.** `TranslatePanel` keeps the ORIGINAL text visible at all times and shows a translated block only on demand. The degraded chip appears whenever `degraded == true` OR `translated == false` (the local rules engine has no translation model, so it returns the original with `translated=false`); both honestly mean "not a live AI translation". API-down falls back to rules (original text) and says so. Translate is offered on incoming message bubbles only (translating one's own text adds nothing).
- **Dedup is a non-blocking pre-submit warning.** Before a help REQUEST is submitted (offers are exempt), `help_flow_screen.dart` runs `aiAssistProvider.dedup(candidate, openRequestFreeforms)`; a near-duplicate pops an `AlertDialog` with "View existing" (closes the flow back to the map) and "Submit anyway" (proceeds). Empty note ⇒ dedup against the selected category labels. No hit, no world state, or an offer ⇒ submit proceeds unchanged. The deterministic rules fallback (Jaccard ≥ 0.5) is preserved for offline.
- **Browser click-through: node PMTiles Range (206) + two-profile zero-error boot verified; UI taps substituted by Dart tests.** A minimal valid raster PMTiles region was generated and served by a real node; the 206 Range response and catalog were asserted over HTTP, and the app booted same-origin in two profiles with zero console errors. The translate/summarize/dedup taps and the PMTiles on-screen render are not drivable in headless Chrome (no aria-label semantics nodes — the confirmed FEAT-003/004/005 limit); their authoritative proof is `ai_assist_test.dart` + the web build. See OVERNIGHT_LOG for the exact ran-vs-substituted record.

### FEAT-007 (Item G) — CORS, signed package manifest, docs honesty sweep

- **Cloud CORS policy = wildcard origin, header-based auth, preflight answered.** `withCORS` in `cloud/internal/api/server.go` wraps the whole mux and sends `Access-Control-Allow-Origin: *`, `-Methods: GET, HEAD, POST, OPTIONS`, `-Headers: Content-Type, Range, X-Api-Key, X-Org-Token, Authorization`, `-Expose-Headers` for Range metadata, and `Access-Control-Max-Age: 86400`; an `OPTIONS` request is answered with `204` and never reaches a route. Rationale: a wildcard origin is safe here because the API carries **no cookies / ambient credentials** — auth is an explicit `X-Api-Key` header the browser never attaches automatically, so a cross-origin page still needs a valid key and the wildcard does not widen what an attacker can reach. This mirrors the node's existing CORS middleware (`node/cmd/resilience-node/main.go`). Note: the node additionally sends `Access-Control-Allow-Private-Network: true` because it is reached on the LAN/localhost from an HTTPS page; the cloud is a public HTTPS origin and does not need it, so it is not duplicated there. Proven by `cloud/internal/api/cors_test.go` (preflight 204 + headers; origin header on a normal request).
- **Manifest signing scheme = detached Ed25519 over canonical compact JSON, verified against a configured trusted root.** The node serves `GET /node/v1/manifest` returning `{manifest, public_key, signature, algorithm:"ed25519"}` where `signature = Ed25519(signingKey, manifest.CanonicalBytes())` (`node/internal/packages/manifest.go`). Canonical bytes = compact JSON (`encoding/json`) of the manifest with entries sorted by `(kind, name)` and struct field order preserved, so the same filesystem state always yields the same signable preimage. Rationale for reusing Ed25519 (not X.509 / PGP): the whole system is already an Ed25519 world (every event is Ed25519-signed), clients already carry an Ed25519 verifier (`Signer.verify`), and a detached signature over a canonical JSON doc is the smallest thing that gives "verifiable against a trusted root" without adding a certificate library. The Dart client (`app/lib/nodes/package_manifest.dart`) reconstructs the identical canonical bytes (same key order, ASCII-only values so Go's HTML-escaping and Dart's `jsonEncode` agree) and verifies against `packagesTrustedRootProvider` (`--dart-define=PACKAGES_TRUSTED_ROOT=<hex>`).
- **Fail-closed, and refuse to serve an unsigned manifest.** If the node has no signing key configured (`--packages-signing-key` / `PACKAGES_SIGNING_KEY` unset), `GET /node/v1/manifest` returns `503` rather than an unsigned manifest — a client must never be handed something that merely *looks* trustworthy. On the client, `verifySignedManifest` returns `untrustedKey` when the embedded key is not the configured root, `badSignature` on any tamper, and `malformed` for an unsupported algorithm or bad payload; a checksum is read ONLY from a manifest that returned `ok`. The key file may be a 64-byte private key or a 32-byte seed (hex).
- **Checksum verification is the trust boundary, not transport.** A downloaded file is trusted only when its SHA-256 equals the entry in a verified manifest (`_verifyChecksum` in `offline_downloads_screen.dart`). Because the integrity comes from the signed manifest + checksum, the bytes may arrive over any channel — including a resumed HTTP **Range** download — without weakening the guarantee. The node already serves files via `http.ServeContent` (206 Partial Content), so a large PMTiles download can resume from a byte offset; `TestRangeResumeDownload` proves a two-part Range fetch reassembles to bytes whose SHA-256 matches the signed manifest.
- **Honest web limitation for on-device download/resume.** A browser has no filesystem, so true background download with a progress bar and a persisted partial file that survives a reload is not possible on web; the UI does not claim it. The checksum verification still runs on web where the platform can fetch the bytes over HTTP (and best from a native build or an HTTPS node, since an HTTPS page cannot fetch a plain-HTTP LAN node — mixed content). The manifest-trust banner shows `verified` / `untrusted` / `unavailable` honestly.
- **Blob storage location (carried forward, recorded here for completeness).** Encrypted attachment blobs live **in memory** on both the cloud (`/v1/blobs/{sha256}`, client-key gated, 2 MiB cap, rate-limited, 7-day purge) and the node (`/node/v1/blobs/{sha256}`, LAN, no key) — see FEAT-003. Durable/off-box blob storage (e.g. S3) is a production decision left open in spec §8.
- **FEAT-005 deliverables verified, not re-implemented.** The HELP_REQUEST close/cancel UI (`_closeRequest` → `HelpRequestClosedBody` in `my_posts_screen.dart`, owner-only) and the auto-hide of supplies past `available_until_ms` (`WorldState.mapResources()` + `ResourceView.isExpired`, used by `map_screen.dart`) were confirmed present from FEAT-005 and left unchanged.
- **Browser click-through: cross-origin CORS win + manifest checksum verified over HTTP; UI taps substituted by Dart/Go tests.** See OVERNIGHT_LOG for exactly what ran vs. substituted.
